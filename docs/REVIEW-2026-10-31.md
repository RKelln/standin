## Assessment

Standin has a useful core and a substantial test suite. The small Go binary, explicit approval,
separate mapping folder, and refusal of many ambiguous inputs are good foundations. The existing
tests pass, including the race detector. All six configured platform targets build.

**I would keep this on invented data until the five high-priority findings below are fixed.**
The new probes found ways to write restored names into an AI-readable folder, put the secret mapping
inside the project, expose extra values through ambiguous column names, and silently assign the same
stand-in to different people. Passing the existing suite does not cover these cases.

This is a source review with targeted tests, not a security certification. No real personal or business
data was used. No fixes to application code were made as part of the review.

### R1. A nested output symlink puts restored names into `scrubbed/`

**Source:** [restore.go](../internal/cli/restore.go), `restoredPath` and `runRestore`;
[store.go](../internal/store/store.go), `WriteAll`.

Restore constructs an output path beneath `restored/`, then follows its parent directories while
creating the temporary file. It does not check where those directories lead.

**Reproduction:** After making a mapping for `Zelda Quorn`, create:

```text
scrubbed/jobs/answer.md       contains: Dear [VALUE_1]
restored/jobs                symlink to the project's scrubbed/ folder
```

Run `standin restore scrubbed/jobs/answer.md`. It exits 0 and reports writing
`restored/jobs/answer.md`. The physical file is `scrubbed/answer.md`, containing `Dear Zelda Quorn`.
The normal hook path check classifies that physical output as `ZoneNone`, so a subsequent Read of it
is allowed. This is stronger than aliasing the whole `restored/` folder, which the hook can recognize.

**Impact:** The person can follow the documented restore flow and place real data directly in the
folder the AI is instructed to read. The link need only exist when the person restores the file.

**Fix:** Enforce destination boundaries at the filesystem operation, not just with path strings.
Refuse symlinked output roots and components for this MVP, or use directory handles with constrained
operations and explicit separation of the raw, scrubbed, restored and private trees. Check nested
components and aliases as well as the top-level directory. A check followed by an unconstrained write
still leaves a race if another process can change the link. Go's standard library provides
[directory-constrained file operations](https://pkg.go.dev/os#Root), which are worth evaluating here.

### R2. A private-folder symlink can put the mapping inside the project

**Source:** [store.go](../internal/store/store.go), `PrivateDir`, `Inside`, `Ensure`.

`PrivateDir` resolves the project path but uses the lexical path of `--private` and `STANDIN_HOME`
when checking whether the secret folder is outside the project.

**Reproduction:** Make an external `alias` symlink pointing to `project/cache/`. Run scrub with
`--private /path/to/alias`. The command accepts it and writes the mapping as
`project/cache/mapping.json`. The probe confirmed that file exists inside the project.

**Impact:** A folder reported as outside the project actually holds the secret mapping inside it.
The Claude hook's own symlink handling provides an additional defense when configured correctly,
but the CLI's storage boundary is still false. Other agents, backups and project-sharing tools may
see the file. Git ignores do not protect it from reads or folder uploads.

**Fix:** Resolve the longest existing part of the private path and validate the remaining components.
Reject private/project overlap through aliases, including case-insensitive paths on supported systems.
Keep the boundary valid while creating and writing the private directory. Add equivalent tests for
`STANDIN_HOME`, not only `--private`.

### R3. Concurrent scrubs lose mappings and reuse stand-ins for different values

**Source:** [scrub.go](../internal/cli/scrub.go), `runScrub`;
[mapping.go](../internal/mapping/mapping.go), `Load` and `Get`;
[store.go](../internal/store/store.go), `WriteAll`.

Each scrub independently reads the mapping, allocates counters, then replaces the mapping file.
There is no lock spanning that read/change/write sequence. Atomic replacement of one file does not
make the sequence exclusive.

**Reproduction:** Start 16 CLI runs at once, each scrubbing one different file in the same project.
Each file contains one distinct invented customer. In repeated review runs, the final mapping had
**one entry**, while all 16 scrubbed files existed. Different files contained the same `[VALUE_1]`.

**Impact:** Restore can silently substitute the wrong person's name, rather than report an unknown
stand-in. This breaks the core round-trip promise and can misaddress a letter or merge unrelated
records. Concurrent use is plausible when agent tools operate in parallel.

**Fix:** Serialize mutations with a lock that works across processes, acquired before loading the
mapping and held through publication. A Go mutex alone is insufficient. Include approve and other
private-state writers in the design. Keep a consistent generation of mapping and scrubbed outputs;
test that every produced stand-in still restores to its own input after concurrent runs.

### R4. Flattened JSON paths merge distinct fields under one keep rule

**Source:** [json.go](../internal/dataset/json.go), `join`, `flatten`, `parseJSON`, `writeJSON`;
[config.go](../internal/config/config.go), column lookup.

Literal JSON keys can contain the same punctuation used to describe nested paths. Distinct fields
are therefore merged into one column before approval and rewriting.

**Reproduction:**

```json
[{"meta.city":"public","meta":{"city":"Zelda Quorn"}}]
```

Approve one `keep` rule for `meta.city`, intending the literal field. Scrub treats both values as
one column, reports one kept column, and writes `Zelda Quorn` unchanged. Similar ambiguity exists
around the array marker `[]` and the synthetic `(key)` column name.

**Impact:** Approval cannot distinguish fields that the parser has combined. A keep rule can expose
another field that should have received the default tokenization rule. The ambiguity can also appear
in a later export while the config and its approval remain unchanged.

**Fix:** Use an unambiguous internal path representation, with escaping for the public config format.
For a smaller MVP fix, refuse reserved key spellings or any distinct structural paths that collapse
to the same config name. Test dotted literal keys, array-marker keys, `(key)`, and empty key segments.

### R5. Duplicate CSV headers apply one keep approval to multiple columns

**Source:** [dataset.go](../internal/dataset/dataset.go), `parseCSV`;
[config.go](../internal/config/config.go), `ColumnFor`;
[review.go](../internal/cli/review.go), approval presentation.

CSV parsing checks row width but accepts duplicate headers. Config lookup uses the header name for
each physical column. Approval presents the config entry once.

**Reproduction:**

```csv
Status,Status
paid,Zelda Quorn
```

Approve `Status: keep`. Scrub exits 0, reports two kept columns, and writes both values unchanged.
The second value also appears in the scrub preview sent to stderr.

**Impact:** One approval expands to an ambiguous set of columns. This can happen in untidy exports
without any hostile input. JSON duplicate object keys already receive a refusal; CSV needs a matching
policy. TSV shares this parser.

**Fix:** Refuse duplicate CSV/TSV headers before shape, approval or scrub. Tell the person to rename
them, using column positions in the message. Check duplicate Markdown table headers too; multiple
separate tables sharing a configured header is an intentional, documented behavior and should remain
a separate decision.

### R6. JSON keys on empty containers bypass the stand-in-input check

**Source:** [json.go](../internal/dataset/json.go), `flatten`;
[scrub.go](../internal/cli/scrub.go), `refuseStandins`.

The input stand-in check visits flattened columns and values. A key attached to an empty object or
array has no scalar descendant, so it is absent from those columns.

**Reproduction:** Tokenize Customer as PERSON in:

```json
[{"Customer":"Zelda Quorn","[PERSON_1]":{}}]
```

Scrub accepts the pre-existing token-shaped key. Restore then writes:

```json
[{"Customer":"Zelda Quorn","Zelda Quorn":{}}]
```

**Impact:** A literal key is silently changed into an unrelated real value. This bypasses the explicit
input refusal introduced to prevent exactly that confusion. Empty-container keys are also absent
from the shape inventory, even though scrub can rewrite their names.

**Fix:** Validate every key and scalar while walking the JSON tree, independently of column
flattening. Include empty containers in the key inventory, hidden-character checks and reserved-token
checks. Test empty arrays as well as empty objects.

### R7. Single-name filenames expose values that were tokenized in the file

**Source:** [cli.go](../internal/cli/cli.go), `dataLikePart`;
[looks.go](../internal/scan/looks.go), `LooksLikeDataName` and `LooksLikeDataHeader`.

Headers receive the newer single-word name check; filenames deliberately use the older check that
mainly recognizes multiword names and patterns. Filename checks also do not compare against known
mapping values.

**Reproduction:** Use `raw/Oksana.csv` with a Customer value `Oksana`. Shape exits 0 and writes the
title `Shape of raw/Oksana.csv`. Scrub replaces the cell with `[VALUE_1]` but writes
`scrubbed/Oksana.csv` and prints the name in its messages.

**Impact:** The AI sees the tokenized person's name in the filename, shape title and command output.
This is an additional metadata leak beyond the header and text misses listed in README.

**Fix:** Apply the single-word header check to filename components, and compare filenames against
known private values during scrub. Prefer neutral generated output names if false positives make
renaming burdensome. Do not print a newly identified private filename in the refusal. Document the
remaining metadata limits explicitly.

### R8. Restore can create an active spreadsheet formula without warning

**Source:** [restore.go](../internal/restore/restore.go), `isFormula`, `Restore`.

The formula guard checks the tokenized cell before substitution. A safe-looking stand-in can expand
into a formula from the mapping.

**Reproduction:** Tokenize a CSV cell containing `=1+1`, then restore its scrubbed CSV. The source
cell is `[VALUE_1]`, so the formula guard allows it. Restore exits 0 and writes `=1+1` as a cell.

**Impact:** Restored content can run as a formula when opened in a spreadsheet, despite the guard.
The probe used harmless arithmetic; it did not execute a spreadsheet or demonstrate exfiltration.
The risk matters when exported records contain untrusted text. CSV quoting alone does not make a
formula inert.

**Fix:** Check the fully restored cell before publication. Refuse, leave the token in place with a
warning, or provide an explicit person-approved mode for active content. Consider the same issue
when restoration introduces a URL or markup; the present link check examines the input, not the
expanded result. Do not promise general HTML or spreadsheet safety from these regular expressions.

### R9. Restore writes malformed JSON rather than refusing it

**Source:** [cli/restore.go](../internal/cli/restore.go), `runRestore`;
[restore/restore.go](../internal/restore/restore.go), JSON and CSV modes.

The JSON validity check runs only when the input was already valid. Invalid input skips it entirely.

**Reproduction:** Restore `answer.json` containing `{"Who":"[VALUE_1]"` with its closing brace
missing. It exits 0 and writes `{"Who":"Zelda Quorn"`, still malformed.

**Impact:** A partial or malformed agent answer is reported as successful. It conflicts with the
project-wide promise to refuse files the tool cannot parse. CSV restoration also deliberately enables
`LazyQuotes` and disables field-count checking, so it is substantially more forgiving than scrub.

**Fix:** Parse structured restore input strictly before using the mapping, then validate the output.
Offer an explicit plain-text route when a person wants to restore an incomplete fragment. Add tests
that assert exit 2 and no output for malformed JSON and malformed CSV. JSON restoration also needs a
duplicate-key check when different token keys restore to the same normalized first spelling.

### R10. Failed init can change the project while saying nothing changed

**Source:** [init.go](../internal/initcmd/init.go), `Run` application loop and `fail` helper.

Init prepares a plan, but creates folders and writes files sequentially without rollback. Every
failure uses a message ending in `Nothing was changed.`

**Reproduction:** Put a regular file named `scrubbed` in a project with `raw/` present and no
`shape/`. Run init. It creates `shape/`, fails at `scrubbed`, exits 2, and says nothing changed.

**Impact:** The failure report is false. Later failures can also leave a partial settings update,
which is harder to diagnose than an extra folder. The probe confirmed the folder case; it did not
inject a disk failure halfway through writing hook settings.

**Fix:** Preflight all existing destination types and permissions. Stage changes and roll back where
possible. When rollback is incomplete, name what changed and what setup remains unfinished. Do not
use the blanket unchanged message after applying mutations.

## Other risks and gaps

These deserve follow-up, but I have not counted them as additional reproduced high-priority bugs.

- **File publication is not a crash-safe transaction.** `WriteAll` renames several files in order and
  attempts rollback on an ordinary error. Rollback errors are ignored, and rollback overwrites old
  files in place. A process kill or power loss can leave a mixed generation. File `Sync` does not
  establish an all-files commit. Define the recovery policy, keep recoverable mapping generations,
  and narrow the absolute “every file or none” claim until fault-injection tests support it.
- **Windows privacy permissions are unverified.** Private files use Unix modes 0700/0600. Go documents
  that Windows `Chmod` uses the owner-write bit for the read-only attribute; it does not establish
  owner-only access. The default user profile may provide appropriate inherited access, but arbitrary
  `--private` locations need a stated policy and native ACL tests. See
  [Go's Chmod documentation](https://pkg.go.dev/os#Chmod).
- **The mapping parser needs stronger integrity checks.** It does not require EOF after decoding,
  verify that stored keys agree with spellings, or reject counter conversion overflow. Word-choice
  loading also decodes only the first JSON value. Test corrupt-but-parseable private files, not only
  broken JSON. Refuse damaged data without regenerating IDs over existing scrubbed outputs.
- **Screen detection is not proof of a person.** A character device other than the null device is
  accepted as a terminal. A pseudo-terminal can be controlled by software, as the tests themselves
  demonstrate. The decision record already recognizes this. The CLI screen checks reduce accidental
  leakage; an OS boundary or trusted harness must provide stronger isolation.
- **Hook coverage is narrower than “before each tool call.”** The PreToolUse matcher enumerates known
  tools. Other tools, including MCP tools, do not enter the unknown-tool refusal branch unless they
  match it. The shell guard is a command-text heuristic. Document the supported tools, keep the
  safety-net wording, and test installed file-reading MCP integrations before recommending them.
- **No-network evidence has a specific scope.** The tests show the current Go dependency graph has no
  network package. Installers and development scripts intentionally download files. Init can launch
  `claude --version`, whose behavior is external to the binary. The package check cannot prove what
  that child process does, or prevent future direct socket syscalls. Keep dependency checks and add
  a denied-network smoke run if a stronger runtime claim is needed.
- **The release workflow is absent from this checkout.** RELEASING names `.github/workflows/release.yml`,
  but `.github/` is absent. HANDOFF explains that CI/release workflows are on an unmerged local branch.
  Until that lands, the automated tag-and-publish instructions are not an implemented release path
  here. I did not publish or install a release.

## External claims checked

The official [Claude Code hooks reference](https://code.claude.com/docs/en/hooks) supports exec-form
hooks with `command` plus `args`, and `onFailure: "block"` starting at v2.1.295. Those choices in
`init` are supported. This review did not repeat the live Claude smoke test or make model calls.

The official [sandbox documentation](https://code.claude.com/docs/en/sandboxing) supports merging Read
deny rules into shell sandbox restrictions. It also says the shell sandbox does not enclose file
tools, MCP servers or hooks, and can be unavailable. The init message saying it blocks “every program”
should state the scope and require checking that the sandbox actually started. The hook process must
retain access to the mapping for its own checks, so that exception is material to the design.

The official [Go JSON documentation](https://pkg.go.dev/encoding/json#Unmarshal) confirms that the
current decoder accepts some invalid string encodings through replacement and allows duplicate
names unless the caller adds checks. Standin already adds useful duplicate-key checks to raw JSON;
its other JSON readers and restore need equally explicit policies.

## What is already working well

- The runtime has no third-party Go modules and cross-builds without cgo for the requested platforms.
- Most processing is staged in memory before output, and the existing refusal tests cover malformed
  CSV, unsupported binary content, hidden characters, unsupported shapes and unapproved rules.
- Config approval is tied to the config bytes; word choices are separately hashed into approval.
- Mapping data stays out of normal reports, and errors often use positions and stand-ins instead of
  real values. The report command avoids printing private filenames and columns.
- Restoration uses exact delimited stand-ins, reports spelling normalization, and avoids fuzzy
  matching. The normalization tradeoff is recorded rather than hidden.
- README explains many real limits: unknown names, common-word names, combinations that identify a
  person, relationship leakage, and the limits of hooks. Keep those limits prominent.
- The latest calendar change has focused tests and a recorded reason. It did not touch the storage
  and parsing paths responsible for the findings above.

## Recommended next steps

1. Fix R1–R5 and add regression tests that assert refusal or correct round trips. Keep the implementation
   small: rejecting ambiguous input is acceptable for this MVP.
2. Fix R6–R9, then cover failed setup and publication with fault-injection tests. Test both normal
   errors and interrupted runs; make recovery messages truthful.
3. Run native macOS and Windows tests, including symlinks/junctions, private-folder access, terminal
   checks, repeated replacement of existing files, and the actual installer packages.
4. Run the live Claude smoke checks after filesystem fixes. Require positive evidence that each tool
   actually ran or was blocked: several current smoke checks pass merely because a chosen name did
   not appear, which can also happen after an unrelated model or authentication failure.
5. Update README and PLAN to one current contract. The old browser MVP, some approval wording, and
   release instructions still require interpreting later decisions. Record adopted fixes and their
   reasons in DESIGN; this report's recommendations are not implemented design decisions.

Not tested here: real records, real-user approval sessions, native macOS or Windows execution,
Windows ACLs, installed-release behavior, notarization/signing, real harness enforcement, adversarial
MCP servers, runtime network tracing, power-loss recovery, or a measured privacy guarantee. The prior
shape-only model trial is recorded in DESIGN decision 23; it was not repeated in this review.
