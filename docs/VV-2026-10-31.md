# Standin V&V review — 2026-10-31

Independent verification and validation of the working tree at `cf62164` plus its uncommitted changes.
Written by a reviewer who did not write the code and did not rely on the fix reports: every claim below
was reproduced from the CLI. The W06 part uses the workshop's own invented bike shop. The real-mail part
used the assistant's own mailbox in a scratch folder; this document reports counts and behaviour from it,
never a value, and none of that data was copied into the repository.

**V&V means two questions.** *Verification:* does the build do what `docs/PLAN.md` says? *Validation:*
does it work for the job it is for — one small-business owner, one workshop participant, their own
records, an agent on the other side?

## Verdict

The code is in good shape. Both questions answer yes, with one new defect and one loop that can stop a
person dead.

- Verification: green on every check I can run here, and all ten findings from the 2026-10-31 review
  are genuinely closed. I re-ran the original probes against the fixed code and they refuse or behave
  correctly.
- Validation: the whole cycle works on the W06 seed data — `init`, `shape`, `approve`, `scrub`, an
  agent answer, `restore`. No name from the data reached the scrubbed tree; every stand-in restored to
  the right value.
- **Real mail, in the form received: refused.** An `.eml` is not accepted (correctly, fail-closed) and
  the refusal gives impossible advice instead of the `.md` route that works. Converted that way, privacy
  held on real messages — no address and none of the named people survived — but approval cost 117
  decisions for six messages and the AI's copy was shredded by tracking-link noise. Details below.
- **Not finished as a piece of work:** 26 modified and 30 new files are uncommitted, `HANDOFF.md` stops
  before this review, and the CI workflows are untracked here while the unmerged `ci-workflows` branch
  holds an older version of them. A crash, a bad checkout or a `git clean` loses the review fixes and
  the workflows.
- **One new defect (F1):** a hyphen or underscore in a file name defeats the name check. The name leaks
  in the shape file and in the first scrub, and the second scrub then blocks the whole batch without
  saying which file. The W06 seed data trips it (`sam-profile-draft.md`).

## Findings

### F1 (P2, new). A hyphen or underscore hides a name in a file name — **fixed**, decision 69

`LooksLikeDataHeader` checks the whole hyphenated stem as one word, so `sam-profile-draft` is not a name,
while `sam profile draft` and `SamProfileDraft` are. `knownDataName` *does* split on `-` and `_`, but it
only knows values that are already in the mapping.

Reproduction, fresh project, two files in `raw/`:

```text
raw/grace-notes.md    "The owner says hello."        (the name is only in the file name)
raw/sam-diary.md      "Sam owns the shop …"
```

- `shape` writes `shape/grace-notes.md.shape.md` and `shape/sam-diary.md.shape.md`. Both start
  `# Shape of raw/grace-notes.md`. **The AI is handed the first name and no warning is printed.**
- `grace` never appears in any file, so it never enters the mapping and is never caught.
- `Sam` appears in the text, so the first `scrub` succeeds and writes `scrubbed/sam-diary.md`. The second
  `scrub` refuses **the whole batch**: "One file name looks like private data… Rename the file in raw/"
  — without saying which of the 18+ files it means.

Why it matters: hyphen and underscore are the ordinary separators in real file names, so this is the
common case, not an edge. The workshop participant cannot act on a message that hides the file name, and
after a move to `scrubbed/sam-diary.md` the hook blocks `raw/` reads until they guess.

Suggested fix, tested: split a file-name component on `-` and `_` before the check, and run the *word*
check on each part (not the digit or pattern checks, and not the joined words). In a copy of the tree,
in `dataLikePart`:

```go
for _, sep := range []string{"-", "_"} {
    if !strings.Contains(stem, sep) {
        continue
    }
    for _, part := range strings.Split(stem, sep) {
        if part != "" && scan.HeaderWords != nil && scan.HeaderWords(part) {
            return true
        }
    }
}
```

`go test ./...` stays green with that change, including the existing `wide-names-as-headers.csv` e2e
case, and the real W06 folder now hides `sam-profile-draft.md` at `shape` and warns. Two traps I hit on
the way, both worth a test:

- Joining the parts and running the whole-string check flags `wide-names-as-headers.csv` (a fixture).
- Checking each part with the full pattern check flags `report-2026.csv` and `top-100.csv`, because a
  bare number reads as data. Those file names are ordinary.

Also worth doing in the same change: in the batch refusal, name the file with only the offending part
masked (`raw/***-profile-draft.md`), and reuse the same anonymous name on a repeated `shape` (F4).

### F2 (P3). Restore normalises case inside a kept string — **open**

Stand-ins are stored by first spelling, so a bank description in capitals comes back in title case:
`Northgate CYCLE SUPPLY`, `E-TRANSFER Tomas Novak`. The command does warn
(`1 stand-in(s) had more than one spelling; the first one was used`), and DESIGN records the tradeoff.
It is still visibly odd in a file a person will open. Either widen the warning to say the case changed,
or keep the all-caps spelling when the surrounding word is all caps.

### F3 (P3). Restore writes LF into a CRLF file — **open**

The W06 CSVs are CRLF. Scrubbed and restored copies are LF, so `diff` reports every line changed and a
byte comparison fails even when every value is right. Harmless for the data, confusing for a person
checking the result, and it makes "round trip" harder to test. Preserve the input line ending, or say in
the README that restore writes LF.

### F4 (P3). Repeated `shape` runs leave stale anonymous shape files — **fixed**, decision 71

A file flagged at `shape` is written as `file_<n>.shape.md`. Running `shape` again picks the next number
(`file_1`, `file_2`, …) and leaves the previous one behind. Either reuse the name for the same file or
say the old one is stale. It is now `file_<6 hex of the path>`, so the same file always gets the same
name and the second run overwrites its own file.

### F5 (contract question). The prompt guard is on, though the trial note asked for it to go — **settled**

`docs/get2know-needs.md` item 2 records Ryan's steer: "Standin is for the data fed to the agent, not for
interactive chat. Remove it from `init`, the hook code, the smoke test, DESIGN 21 and the docs."
DESIGN decision 32 instead keeps it with `init --no-prompt-guard`. The reasoning is written down, but it
reverses a stated requirement without citing it. **This is Ryan's call**, not a bug.
Settled by the author on 2026-10-31: the guard stays, configurable is enough. No code change; the
sentence above stays as the record of the disagreement and its resolution.

### F6 (P3, new). A refusal hid the file name even when the person had just typed it — **fixed**, decision 70

`standin shape raw/ledger.xlsx` answered "A raw file (name hidden): I cannot read spreadsheet files like
this one". Echoing a path the person just typed discloses nothing, and with twenty files in `raw/` the
message is a dead end. The reason for hiding is real — a name is only known to be private once every
value has been read — but it applies to a batch run, not to a named one. Named files are now named back;
a batch run prints the extension ("a raw file (name hidden, .xlsx)"). The extension is echoed only when
it is plain lowercase alphanumerics, because a file called `.Zelda Quorn` carries its name where the
extension would be — the existing test suite caught that on the first attempt.

## Real mail, in the form received

Separate test, 2026-10-31. Six messages exported from the assistant's own mailbox with
`himalaya message export <id> -F` — full RFC 822 as the server holds them, headers, MIME parts,
quoted-printable and tracking links included. The mailbox (40 messages) is all bulk mail: art-listing
newsletters, LinkedIn notices, one Substack letter. **It holds no one-to-one human correspondence**, so
the friendly-reply case is not covered here; the W06 plain-text messages stand in for that. Everything
stayed in a scratch folder; no value from it appears in this document or in the repo.

**As received, `.eml`: refused, correctly.** `shape` exits 2 on every file: "I cannot read this kind of
file. Save it as CSV, or remove private details by hand." Fail-closed is right. The advice is not: an
`.eml` cannot be saved as CSV, and the message never mentions the route that does work (paste the
messages into a `.md` file, as the README says).

**Saved as `.txt` (the likely user move): accepted, but degenerate.** The file parses; the MIME headers
become 31 `Label: value` "fields" and the body is one long `text` block. Between the two files the word
check produced **379 candidates**, mostly quoted-printable and CSS fragments.

**The documented route — decoded messages pasted into one `.md`:** works. 266 lines, 6 messages:

| Measure | Result |
| --- | --- |
| Stand-ins written | 158 (117 NAME, 11 EMAIL, 10 PERSON, 8 ACCOUNT, 3 POSTAL, 2 ADDRESS, 7 VALUE) |
| Word decisions at `approve` | **117 for 6 messages, six screens** |
| Email addresses left in the scrubbed text | 0 of 16 |
| People named in headers or bodies left in the scrubbed text | 0 — checked full names and first names alone |
| Capitalised two-word names still present | 37 of 66 — galleries, funds, cities, exhibition titles |
| Size of the AI's copy | 433 stand-in tokens in 266 lines |

The privacy half holds: every person named in that mail is gone from the copy, addresses and account
numbers included. The reading half does not: the file the AI gets is shredded. One tracking token
becomes `[NAME_19]2[NAME_20]2[NAME_21]…`, and the sending service's own domain is tokenized
(`https://www.[PERSON_10].com`), so the agent cannot even tell which platform a notice came from.

Classified, the 117 decisions were: 78 ordinary words, 19 base64/hex fragments, 24 very short tokens,
7 whole URLs, 6 font or service words. Most of that is link noise the person must page through. Pressing
Enter to keep none — the obvious response to six screens — leaves the document unreadable.

`restore` on that file gave back 51 differing lines out of 266: seven first-spelling changes, and every
value that sat inside a link left as a stand-in (by design, with one warning). A restored email is
therefore not a faithful copy of the original.

### G1 (P2). The `.eml` refusal sends the person the wrong way — **fixed**, `.eml` is supported

"Save it as CSV, or remove private details by hand" is impossible advice for a mail file and hides the
route that works. Name the format and the workaround: *"I cannot read email files yet. Save the messages
as text in a `.md` file (From, Date, Subject, then the message), or remove private details by hand."*

### G2 (P2). The word check counts URLs and base64 as words — **partly fixed**, decision 72

This is why real mail costs about 20 decisions per message against 0.4 in the W06 text set, and why the
scrubbed copy is unreadable. Two small changes would fix most of it: skip tokens inside a URL or a
`key=value` query string, and skip base64/hex-like runs and bare digits. A third, larger one: notice an
HTML body and say so, rather than passing it through the word check.

Long encoded runs are now one candidate each (decision 72): a 16-character tracking id went from three
decisions ("AQH", "JzLm", "Pq") to one. Bare digits are already skipped. A plain link made of ordinary
words still costs nothing, and a link that holds a name is still the documented miss. Not done: saying
"this body is HTML" rather than word-checking it.

### G3 (P3). Say what restore leaves behind in a link — **fixed** in the README

The README's restore section describes formula and link checks, but not the outcome a mail reader meets:
the value stays a stand-in, permanently, and the file is not a copy. One sentence in "If a save stops
early" or the restore notes would save a support question.

## Email support (added 2026-10-31, after this review)

Ryan asked for `.eml` support and a synthetic message. Two changes landed in the working tree:

1. **`.eml` is a supported input** (DESIGN 68, contract in PLAN "Email"). One message per file is
   rendered to `From`, `To`, `Cc`, `Date`, `Subject` plus the body text, and every existing rule
   (config, shape, approve, scrub, restore, hooks, check) applies unchanged. The plain part is
   preferred; HTML-only messages are converted and lose links and pictures; attachments are counted and
   never opened; `message/rfc822` is read as a forwarded message. `.mbox` and `.msg` are refused.
   `net/mail` and `mime/multipart` are not used because both link `net`; the multipart split and the
   HTML-to-text step are in `internal/dataset/email.go`.
2. **F1 is fixed** (DESIGN 69): a hyphen or underscore in a file name no longer hides a first name.
   `sam-notes.md` is now hidden at `shape` and refused at `scrub`; `report-2026.csv`,
   `invoices-q3.csv` and `wide-names-as-headers.csv` are unaffected.

Synthetic fixtures: `testdata/mail/` — eight files made by `tools/make_fixtures.py`
(`simple`, `alternative`, `html-only`, `base64`, `attachment`, `forwarded`, plus `bad-charset` and
`mbox` for the refusals). All invented names, `example.com` addresses, 555-01xx numbers.

The parser is also checked against `github.com/emersion/go-message` in the test binary only: both read

HTML-only messages lose their links, `.mbox`/`.msg` are refused, only UTF-8/US-ASCII/ISO-8859-1/
Windows-1252 are decoded, and the scrubbed message is a view rather than the original file.

## What this review could not test

Native macOS and Windows runs and Windows ACLs; the hosted CI workflows (never run); the installers on a
clean machine; a live Claude Code session (`tools/claude_smoke.sh` was not run — no model calls were
made); real user approval behaviour; power loss. Real mail was tested, but only bulk mail: **no
one-to-one human correspondence exists in the assistant's mailbox**, so the customer-reply case rests on
the W06 plain-text messages. A process running as the same OS user can still control a pseudo-terminal,
move an open directory, or read the private folder. Fail-closed and the hooks are a safety net, not a
sandbox.
